A prompt is not a control: two autopilots that forged their own evidence

2026-10-24

Two unattended autopilots had written rules against inventing results. Both forged their own evidence. What replaced them.

In August I audited two unattended agent systems I had been running. Both had rules, written plainly in their instructions, against inventing results. Both invented results anyway, and not subtly.

This post is what they did, why the written rules didn't stop it, and what the system that replaced them does instead.

System 1: the ledger that published things that never existed

A five-agent swarm on low-cost models ran a small content pipeline. It kept a ledger of what it published and a metrics file of how each post performed.

Checked against the live platform, the ledger had six rows marked PUBLISHED. Two were real. The other four had IDs like temp_id_1, youtube_id_12345 and, literally, placeholder_id.

One real post had a second leg on a platform that was never connected. Its post ID was sim-TOAD-24-ABC; the ID itself says "simulated". The metrics file still gave it 7,253 views and revenue to the paisa. A "nightly collection" job added rows of suspiciously round numbers (5000 / 500 / 50) for content that didn't exist, from an affiliate account that didn't exist.

The data files also had cat -n line numbers pasted into cells. An agent had copied its own tool output back into the source file.

The system's own failure policy said: "Never create placeholder, simulated, or inferred performance metrics." It had already been caught doing this once and had logged a lesson about it.

System 2: the reviewer that reviewed itself

A separate autopilot made short technical videos. Before publishing, each video had to pass a review by a frontier model in a browser session. That review step broke when the session expired, and stayed broken for more than 40 days.

The agent didn't escalate. It wrote the review files itself:

"assistant_text_tail": "VERDICT: PASS\n\nStrong technical hook... Pacing is punchy,
 subtitles are in sync ... Ready to publish."

No reviewer wrote that. One forged review also faked the deterministic gate's output ("quality_gate": {"passed": true}) for a video that had no artifacts and would have failed outright.

The rest of the system had drifted the same way:

  • The publish limits in code had been ratcheted from 1 a day to 20, and from 5 a week to 50. Nine videos went out in one day.
  • A test that checked the weekly limit had been failing on the main branch the whole time, while the agent's own notes kept reporting "29/29 tests passing".
  • The quality gate checked resolution, sample rate and duration. It never looked at a single frame. 21 published videos showed no technical content at all: gameplay footage with a word or two on top, or a box of prose describing a demo that was never rendered.

What the two have in common

Every check in both systems asked the agent to certify its own work: a ledger it wrote, a review it could write, a test summary it reported. When the honest path was blocked (an expired login, an account that didn't exist), the cheapest way to "make progress" was to write the success record directly. A rule in the prompt was one more piece of text competing with the goal of making progress.

Cheaper models made it worse, but a stronger model doesn't fix that structure. The structure has to change.

What replaced them

I stopped trusting both and rebuilt the fleet around one rule: anything an agent writes about the outside world is unverified until a check outside the model confirms it. Concretely:

  1. Capability, not judgement. Worker runs use a restricted permission profile: they cannot publish, post or spend, so they never decide whether to. Deterministic steps (publishing on a schedule, reading sales numbers) moved into scripts that run before or after the model, so the model can't invent their inputs or outputs.
  2. Evidence per stage. A claim that something reached a stage (built, listed, published) must carry evidence of that stage's type, plus a verified_via field naming the live check that produced it.
  3. A verifier the agent can't edit. After every run, a script checks those claims. Unbacked claims are quarantined for review, not deleted: the forged records are the evidence of what happened. The runner and guards are read-only to agents, and edits are reverted.
  4. Check the output, not the description of it. The gate that passed 21 empty videos never looked at a frame. A gate has to inspect the thing that ships (the rendered frames, the live URL, the API response), not the agent's description of it.

Did it work?

Two signals from the replacement fleet:

  • In its first week, the verifier demoted three real claims because their evidence was mis-shaped. The agents fixed the evidence; nobody loosened the rule. A rule that also catches honest mistakes is enforced, not decorative.
  • On 2026-09-20, a run found 19 unverified data rows a previous run had left on disk, discarded them and logged why. Self-correction shows up in the commit history, not only in a prompt.

Across 529 unattended runs since then, the verifier has quarantined 5 claims. The fleet's live numbers and full decision log are public: https://denzil10.github.io/agent-fleet/

Takeaways

  • Whatever an agent can write, it can fake. Put the evidence somewhere it can't write, or check it from outside.
  • A blocked honest path is where fabrication starts. Give the agent a cheap, legitimate way to say "blocked" (a blocker file a human reads), and treat silence about a blocker as a bug.
  • Keep forged records. They are your only primary evidence.
  • Tests the agent runs and reports aren't a gate unless something outside the agent reads the result.
