Letting agents drive a real browser on the Mac I'm typing on

2026-10-24

Headless Chrome walled over one User-Agent token, macOS clamping off-screen windows, minimized-but-focused popups, and sign-in windows that leaked for days.

My agents run all day: hourly fleet runs, scheduled jobs, a reviewer that asks a frontier model in a browser tab for a second opinion. Many of those steps need a real, logged-in browser, not an HTTP client. And the machine they run on is the laptop I'm working on.

That gives the problem two sides. The agent needs a browser that behaves like a person's: real profile, real sessions, real user agent. I need it never to show up on my screen or take my keyboard mid-sentence. Here is what it took, in the order the failures showed up.

1. Headless got walled because of one word

Headless Chrome is the obvious way to stay off the screen. On chatgpt.com it hung forever on Cloudflare's "Just a moment..." page.

It wasn't fingerprinting, mouse movement or anything exotic. Headless Chrome puts the token HeadlessChrome in its User-Agent header. With the same profile, headless, swapping in the exact UA headed Chrome sends (major version read from the installed binary, reduced to major.0.0.0 the way Chrome reduces it) gave the logged-in composer instead of the challenge.

Lesson: before building a stealth stack, diff what your headless browser sends against what a normal one sends. The cheapest difference is often the one that matters.

2. Some sites still need a headed browser, and macOS fights you

A few flows refuse headless entirely. So I needed a headed Chrome that is never visible.

The first idea, --window-position=-10000,-10000, failed. macOS clamps a window that sits on no display onto the nearest one. My external monitor is to the left of the laptop, so the "hidden" window landed in full view on it, and Chrome un-hid itself on every new page.

What works:

  • Start Chrome with no window at all (open -j -g, --no-startup-window).
  • Create every page through CDP Target.createTarget with windowState: "minimized", background: true, focus: false. Playwright's context.new_page() opens a normal window that can only be minimized after it has been shown, which is a visible flash.
  • The page still reports visibilityState: "visible", so sites that throttle background tabs load normally.

3. Hidden pixels are not hidden focus

A minimized window still takes keyboard activation when it's created, and an OAuth popup does exactly that. I would be typing into my terminal and the keystrokes would go to Chrome.

The fix is a small focus guard: poll the frontmost process every 2 seconds and hide Chrome only when Chrome is frontmost. Both halves of that rule came from bugs:

  • Hiding Chrome when it wasn't frontmost reshuffled the macOS activation stack and bounced me into an unrelated app.
  • Re-activating "the app that was frontmost before" is wrong because that memory goes stale.

I verified it by sampling the on-screen window list every 50 ms while ChatGPT loaded: zero on-screen windows, and Chrome never took the foreground.

4. Windows leaked for days

Sign-in windows piled up in the Dock for days. Two causes:

  • When an agent attaches to a long-lived Chrome it doesn't own, close() tore down nothing.
  • An OAuth popup is opened by the site via window.open, so it never passes through the caller's code.

Now every page created while attached is tracked, identity-provider pages are closed on teardown, and the shared browser lock sweeps leftover auth popups when it's released. That last part catches jobs that were killed and never ran their own teardown.

Two traps while writing that cleanup:

  • For a page Playwright didn't create, page.url stays '' forever, and framenavigated doesn't fire. Read location.href through evaluate instead.
  • A Google sign-in popup on an already-signed-in profile doesn't stay on accounts.google.com. It lands on myaccount.google.com, so both hosts count as auth popups.

A reaper (launchd, every 120 s) also closes any headless or hidden Chrome with no CDP client for 5 minutes.

5. Three modes, one rule for when a human is needed

The result is three modes behind one call:

Mode Used for On screen
headless everything that works headless never
hidden sites that refuse headless no: minimized, focus-guarded
handover a blocker only I can clear (login, 2FA, CAPTCHA) yes

There is one Chrome per profile. A hidden caller evicts a headless one; a handover window is protected for 30 minutes and is never reaped while I'm using it. An agent that hits a CAPTCHA doesn't guess or retry. It opens a handover window and files a blocker.

What I'd tell someone building this

  • Most "bot detection" failures I hit were one header or one window flag, found by diffing against a normal browser.
  • Test invisibility by measuring the window list, not by looking. I only trusted it once a 50 ms sampler showed zero windows.
  • Anything an agent opens, it must also close, including pages it didn't open itself.
  • Give the agent a clean way to ask a human. A blocker it can file is better than a CAPTCHA it tries to solve.
