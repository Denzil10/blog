88% of my AI coding usage is the model rereading itself

2026-10-25

Token-saving tools shrink what the model writes. I measured where my usage goes: what it writes is 12%. The other 88% is context, and that's where the real savings were.

Every popular token-saving trick for coding agents goes after the same thing: what the model writes. Terser replies, compressed prose, shorter code, filtered shell output.

So I measured what I was actually paying for. Over 35 days of my own coding-agent sessions, everything the model wrote, replies and code included, came to 12% of usage. The other 88% was the model rereading context it had already seen: the system prompt, tool definitions, file contents and the conversation so far, sent again on every request.

Those tools were trimming the 12%.

Where it goes

Two weeks later I measured again, more finely: 7 days, 11.7k requests.

Cache read 50%
Cache write 35%
Output 16%

Share of usage, 7 days, 11.7k requests.

  • Cache read (50%): the context reused from the cache on each request. It's cheap per token, but every turn pays it again.
  • Cache write (35%): context written to the cache. Per token, this is the expensive one.
  • Output (16%): everything the model generated.

A typical session peaked at 95k tokens of context, and one in ten passed 266k. Every turn near that peak rereads all of it.

The usual suspects, measured

Shell output filters. I counted ANSI codes, carriage-return progress bars and repeated lines in my agents' shell output: 0.72% of it. The harness already pages large file reads and stubs out unchanged re-reads. There was almost nothing to filter.

Third-party token savers. Independent tests of the popular tools put most of them within about ±7% on total cost, and some made it worse. Self-reported savings are usually measured against the slice the tool touches, not the whole bill.

What actually moved it

All context-side, each measured before and after:

Change Measured effect
Defer tool schemas a session doesn't use −13.7k tokens on every request
List 51 unused skills by name only, drop 3 unused tools first request 25.0k → 18.7k tokens
Compact earlier (window 300k → 200k, later 150k) ≈ −18% context tokens for the first step (simulated on my transcripts)
Compact idle sessions before the 1h cache expires avoids a full rewrite when you come back
Run general-purpose subagents on a cheaper model they were 15% of a day's usage on the top model

The first two compound. Every request re-sends the tool definitions, so 13.7k tokens saved per request across thousands of requests a week outweighs any amount of terser replies.

The hidden one: full rewrites

16% of my usage went to rewriting a session's entire context into the cache instead of reading it: a whole session's worth of the expensive token type, at once. The causes, from the logs:

  • Switching accounts (7%): the cache belongs to the account, so every open session rebuilds on its next turn.

  • Idle for more than an hour (5%): the cache expires, so the next message rebuilds everything. Built-in idle compaction now runs at about 54 minutes, so the rebuild is a short summary.

  • Right after compaction (2%): unavoidable, but cheap once the summary is small.
  • First request of a session (1.5%): this is what the skill and tool trimming shrank.

None of this shows up if you only look at how long the replies are.

The takeaway

Before you install a token saver, split your usage into read, write and output. If output is a small slice, and for agent work it almost always is, shorter answers can't save much. The savings are in what gets re-sent every turn: tool definitions, skills, stale context, and the full rewrites when a cache expires.

Measure first. Then cut the 88%.
